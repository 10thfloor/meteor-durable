# durable:keyring

> Threshold-signed methods for Meteor — a method that runs only after *t of n* custodians co-sign, using real FROST-ed25519 with a distributed key ceremony. No single server ever holds the key.

Part of the **[meteor-durable](../../..)** exploration of new Meteor primitives. Experimental / proof-of-concept.

```js
import * as frost from '/imports/frost/frost';

export const Treasury = Meteor.keyring({
  name: 'treasury',
  scheme: 'frost-ed25519',
  keygen: 'dkg',                                     // no trusted dealer
  threshold: '3-of-5',
  custodians: () => Meteor.users.find({ 'profile.role': 'finance-signer' }),
  suite: frost,
});

export const pay = Treasury.method({
  name: 'pay',
  schema: { invoiceId: String },
  async run({ invoiceId }) { /* runs ONLY after 3 of 5 custodians co-sign */ },
});

await pay({ invoiceId });   // creates a pending op; resolves once a quorum signs
```

## Why

Some actions shouldn't be one server's call to make — moving money, a
production deploy, an irreversible delete. Threshold signatures require a
**quorum of humans** to co-sign, cryptographically rather than by policy. This
package runs the whole ceremony on Meteor's existing substrate: signing shares
live on the custodians' devices, partial signatures travel over DDP, the pending
"needs your signature" inbox is a reactive publication, and the aggregated
result is a **standard ed25519 signature** any verifier accepts.

It's a natural fit for human-in-the-loop over AI agents: an agent (see
[`durable:mcp`](../mcp)) can *request* `pay`, but three people still have to tap
approve.

## Install

```sh
meteor add durable:keyring
```

Requires **Meteor 3.0+**, `accounts-base`. You supply the crypto `suite` (the
FROST implementation) — this package is the protocol state machine; the math is
pluggable. The `meteor-durable` repo ships a suite at `imports/frost/frost.js`
built on [`@noble/curves`](https://github.com/paulmillr/noble-curves).

## Distributed key generation (no dealer)

With `keygen: 'dkg'`, the group key is co-generated by the custodians' devices
via a **Pedersen DKG** — no party ever computes or holds the group secret.

1. **Round 1** — each device samples its own polynomial, publishes a Feldman
   commitment plus a Schnorr proof-of-knowledge, and an ephemeral X25519 key.
2. **Round 2** — each device sends every other participant their share,
   **end-to-end encrypted** (X25519 → SHA-256 → XChaCha20-Poly1305). The server
   relays ciphertext only.
3. **Finalize** — each device verifies every proof and VSS-checks every share,
   then derives its long-term signing share (which stays on the device) and the
   shared group public key.

The server stores **zero secret material** for a DKG keyring. (`keygen: 'dealer'`,
the default, keeps a simpler trusted-dealer keygen for comparison.)

## Signing

Calling a keyring method creates a durable *pending operation*, not an
execution. Custodians then co-sign in two FROST rounds — both on-device:

```js
// on each custodian's client
const inbox = Treasury.pending();   // reactive cursor of ops awaiting signatures
await Treasury.approve(op._id);      // round 1 (commit) here; round 2 completes automatically
```

At `t` signatures the server verifies each share, aggregates them into one
ed25519 signature, verifies it (RFC 8032), and only then runs the method body.
The threshold is configurable (`'2-of-3'`, `'3-of-5'`, …).

## API

| Call | Where | Description |
|------|-------|-------------|
| `Meteor.keyring({ name, scheme, keygen, threshold, custodians, suite })` | both | Define a keyring. |
| `keyring.method({ name, schema, run })` | server | A method gated behind a quorum. |
| `keyring.pending()` | client | Reactive cursor of ops awaiting signatures. |
| `keyring.approve(opId)` | client | Co-sign as the current user (both FROST rounds). |
| `keyring.info()` | client | `{ t, n, groupPublicKey, status, … }`. |

Ops are idempotent by args-hash, so a retried/replayed caller re-attaches to the
existing pending op instead of asking for a second quorum. Runs and ceremonies
resume on server restart.

## Security

The FROST/DKG implementation was reviewed by an adversarial audit. The
confirmed issues — all **denial-of-service by a malicious participant** (none
allowed forging a signature or leaking a share) — are fixed: the Feldman
commitment degree is bound to `t`, proof and commitment points must be
prime-order/non-identity, X25519 keys are validated, and round-2 payload sizes
are bounded. See the changelog in the source comments for detail.

### Key binding

Three bindings tie every signature and every key to its origin (the first two
are RFC 9591; the rest were added after a second, binding-focused audit):

- **Signature ↔ session**: FROST binding factors tie each signature share to
  the message *and* the full commitment list (anti-ROS).
- **Signature ↔ purpose**: the signed message is always
  `keyring|method|argsHash|opId` — a signature cannot be replayed as any other
  operation.
- **Proof ↔ ceremony**: every DKG round-1 proof-of-knowledge commits to a
  per-session context `Φ = H(keyring | t-of-n | roster | session nonce)`.
  This **fails closed** — the suite refuses to produce or verify unbound
  proofs, so a round-1 package cannot replay into a different ceremony
  (including re-keys of the same keyring).
- **Key ↔ transcript**: when a DKG completes, the new key's *first act* is
  co-signing its own birth certificate — an ordinary t-of-n `confirm` op over
  the canonical transcript hash (keyring, sessionId, Φ, roster + public
  shares, every round-1 package, the finalize set, and the group key). The
  aggregated signature is stored as `provenance` on the keyring doc, with the
  exact signed message (`provenance.msgHex`) so anyone can verify it as plain
  ed25519 from public data alone. Provenance is epoch-guarded and write-once:
  a stale confirm op from a superseded key can neither certify nor block its
  successor.

**Accepted limitation** (deliberate, documented): participants read `Φ` and the
roster from the server-relayed session doc rather than attesting them with
device keys — under this trust model the server already controls roster
presentation. Cryptographically binding the roster to custodian devices
(WebAuthn-signed round-1 packages) is the next rung, not claimed here.

## Status & limitations

This is a proof-of-concept, not audited for production use.

- **Trusted-dealer under `keygen:'dealer'`; DKG under `keygen:'dkg'`.** The DKG
  is real, but uses **ephemeral, unauthenticated X25519 keys** — binding them to
  custodian identities (to stop a malicious relay MITM'ing round 2) is left to a
  real deployment.
- **No complaint/justification round.** A malicious participant who sends one
  recipient a VSS-invalid share stalls the ceremony (loud, recover-by-restart
  DoS) without being blamed. A production Pedersen DKG adds a complaint round.
- **Shares are device-local** under DKG (here: `localStorage`). No dealer, no
  escrow — losing a device loses that share. That's the correct threat model;
  production would add device-held backups or resharing.
- **All `n` custodians must be online** to run the ceremony (true of any DKG).
- Reactive resharing when the custodian set changes is not implemented.
- Crash recovery is **at-most-once by default**: an op that dies mid-execution
  parks as `interrupted` (the action may or may not have run) until someone
  calls `keyring.resolveInterrupted(opId, { outcome })`. Declare a method
  `retry: true` to assert it's idempotent and re-enter signing instead —
  `run()` receives `this.opId` so actions can key their side effects on it.
- One *active* op per `(keyring, method, args)` is enforced by a unique
  partial index, so concurrent identical calls join the same op.
