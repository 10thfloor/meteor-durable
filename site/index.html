The aha

There is no state to lose.
The run is its history.

Every durable operation appends one entry to a journal — a plain document in the Mongo you already have. That one document does four jobs other stacks buy separately: it's the crash recovery, the chat UI, the branch point, and the audit trail. This is the entire trick. Everything else on this page is a consequence.

recv(say)user→ think#1.0model→ act:fetchtool→ recv(approval)human ok→ cosign:signt-of-n→ drain(say×1)steering→ think#1.2yield

1 · Crash recovery

Resume = replay. Recorded steps return their results without re-running, then execution goes live at the frontier. A hash of every prompt is checked on replay — drift fails loudly.

2 · The chat UI

The transcript isn't synced from the agent — it is the journal, published over DDP. Any framework, zero streaming code.

3 · The branch point

Fork a run at any entry and seed a different instruction: same history, different future. What-if timelines and judgment tests, for free.

4 · The audit trail

Who approved, who signed, what the model saw, what each tool returned — already recorded, because recording it is how the system works at all.

And this is everything you wrote

No queue, no state store, no orchestrator sidecar, no websocket layer. Declare the agent the way Meteor taught you to declare a collection, then address it by key from anywhere: Assistant(taskId).say(…).

The model is pluggable — a registry name, anthropic:…, or your own { complete }. Budgets are enforced, per-turn usage is journaled, and a deterministic mockModel makes the whole thing testable without an API key.

server/assistant.js — complete
export const Assistant = Meteor.agent({
  name: 'assistant',
  model: 'anthropic:claude-sonnet-5',
  instructions: 'Do the task. Get sign-off before anything irreversible.',
  tools: [search, release],   // release parks for a threshold co-sign ↓
  memory: Brain,
  budget: { steps: 8, spend: '$0.50' },
});

The 2026 question

Can your agent do the irreversible alone? No. Cryptographically no.

Every tool carries a gate in its type, and the run durably parks at each one — for minutes or for days, across restarts. The top rung isn't a y/n prompt: it's t-of-n threshold signing (FROST-ed25519), under a group key the custodians co-generate in their browsers. The private key never exists on the server — there is nothing for a prompt injection, a rogue tool, or a stolen database to steal.

auto

Just runs

Plain Meteor.method callables. Look things up, compute, draft. The result lands in the journal like everything else.

ask

One human says ok

The run parks until someone calls approve() or deny(reason) — a reactive inbox, not a terminal prompt. Timeouts auto-deny, and even the timeout is journaled.

cosign

A quorum signs

A keyring method: a threshold you choose — 2-of-3, 5-of-9 — each signer contributes a share and the aggregate verifies as plain ed25519. The agent proposes. Humans dispose.

Consequences of the journal

Everything a serious harness has.
Each one is a journal entry.

Steering, interrupts, compaction, forking, memory — the features you know from the best CLI harnesses, except here they're not a process on someone's laptop. They're rows in your database, so they survive, sync, and audit like everything else in your app.

Steer it while it works

Messages sent mid-task queue in a mailbox and inject at the next safe point — between steps, exactly like a harness pumping its input queue. Interrupt yields the turn; nothing queued is ever lost, even across a restart.

→ drain(say×1) · drain(interrupt×1)

from any client
Assistant(id).say('check the failing tests first');
Assistant(id).interrupt();     // ESC, durably
Assistant(id).messages();      // live transcript
Assistant(id).status();  // thinking · awaiting-approval · idle

Fork the timeline

Branch a run — even a finished one — before any decision, seed one steering message, and get the timeline where the payment never happened. The shared prefix replays from the journal, so no side effect ever fires twice. It's also a test harness: attack every decision point and assert the gated tool never fires.

→ forkedFrom: { key, at }

what-if, for real
const branch = await Assistant(id).fork({
  before: 'think#1.1',          // the big decision
  say: 'Take the conservative path instead.',
});
// same history · different future · zero re-fired effects

Memory with three doors

Working memory is the journal. Long-term memory is a keyed, full-text store — and compaction distills into it inside the journaled step, so memory formation is exactly-once. Agents, MCP clients (Claude Desktop, Cursor…), and a live user-facing panel all share the same brain. External clients even get memory_get_last answered from the agent's actual journal — no honor-system checkpoints.

→ compact#0 · remember · recall

one brain, three doors
export const Brain = Meteor.memory({ name: 'brain' });

Meteor.agent({ name: 'assistant', memory: Brain }); // agents
MCP.server('brain', { tools: Brain.mcpTools() });   // MCP clients
Brain('user/prefs').watch();                        // humans, live

On Atmosphere

Seven packages. Take what you need.

Each stands alone; they compose because everything is a keyed handle — Fulfill(orderId), Budget('eng'), Assistant(taskId). If you can address a Collection, you already know the API.

durable:workflow0.1.0

The foundation: journaled, crash-resumable runs. step / receive / sleep / drain / fork, saga compensation, exactly-once triggers.

$ meteor add durable:workflow
durable:agent0.2.0

The harness on top: steering, interrupts, compaction, forking, budgets, gates, model registry, drift guard.

$ meteor add durable:agent
durable:keyring0.1.0

The top gate: FROST-ed25519 threshold signing with Pedersen DKG. Keys live with humans, never the server.

$ meteor add durable:keyring
durable:memory0.1.0

Long-term memory: keyed scopes, full-text recall, session checkpoints, and the standard mcp-memory surface.

$ meteor add durable:memory
durable:mcp0.1.0

Speak MCP both directions: mount methods as tools at /mcp/name; outside agents inherit your gates.

$ meteor add durable:mcp
durable:entity0.1.0

Keyed serialized actors with reactive state — one method queue per key, concurrency by construction.

$ meteor add durable:entity
durable:lens0.1.0

Bidirectional views: rename, redact, scope. Least-privilege context for models as a schema concern, not a prompt plea.

$ meteor add durable:lens

Why Meteor

The same move, one level up

This worked once before.

2012

Real-time by default

Everyone was hand-rolling sockets, cache invalidation, and sync. Meteor's answer: put data on the wire, make every query a subscription — and a chat app became an afternoon. Messages.find().

2026

Durable by default

Everyone is hand-rolling agent state, approval flows, and memory sidecars. Same answer, one level up: put state on the journal, make every run a subscription — and a production agent becomes an afternoon. Assistant(id).say().
